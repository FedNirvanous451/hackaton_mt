# Транспортный бэкенд

Бэкенд принимает NDTP-телеметрию и локальные исторические CSV, связывает `unit_id` с `tr_id`, сопоставляет данные с плановыми и фактическими прибытиями, очищает координаты и рассчитывает признаки. Прогноз получается через **неизменённый API команды ML** из `ml_core/api/main.py`. HTTP и WebSocket отдают данные фронтенду. Старый `model/` и тестовая HTML-карта не используются.

## Запуск

Для запуска всей панели, ML, бэкенда и эмулятора из корня проекта:

```powershell
docker load -i dataset/ndtp-telemetry-emulator.tar
docker compose up -d --build
```

Для запуска только бэкенда и ML:

```powershell
docker compose -f backend/compose.yaml up -d --build
```

- Swagger бэкенда: <http://127.0.0.1:8000/docs>
- Swagger ML-команды: <http://127.0.0.1:8081/docs>
- Проверка бэкенда: <http://127.0.0.1:8000/health/ready>
- Проверка модели: <http://127.0.0.1:8081/health>
- Приём NDTP: TCP-порт `9201`

Compose собирает ML-сервис непосредственно из `ml_core/Dockerfile`, опубликованного командой ML. Бэкенд обращается к `http://ml:8000/predict`; на хосте ML API доступен на порту `8081`. Для подключения внешнего сервиса задайте `ML_SERVICE_URL` перед запуском Compose. `ML_HISTORY_MINUTES` ограничивает хранимую историю телеметрии (по умолчанию 15 минут). `CORS_ORIGINS` задаёт разрешённые адреса фронтенда.

Папка `dataset/` должна лежать в корне проекта. Она **игнорируется Git**, не попадает в Docker-образ и монтируется в контейнер бэкенда как `/srv/dataset` только для чтения. Если её нет, текущий NDTP-контур продолжает работать, а исторические маршруты отвечают `503`. По умолчанию читается `validate`; для `train` или `test` задайте `DATASET_SPLIT`.

Без Docker запустите `uvicorn api.main:app --port 8081` из `ml_core`, затем из корня проекта в другом терминале:

```powershell
$env:ML_SERVICE_URL = "http://127.0.0.1:8081"
python -m uvicorn backend.app.main:app --port 8000
```

## Текущий поток NDTP и расписание

1. Источник расписания отправляет `POST /api/v1/arrivals` с ID прибытия, ID автобуса, временем и координатами остановки. Бэкенд выбирает первое прибытие в строгом окне `(T+10 минут, T+15 минут]`.
2. Пары `unit_id`/`tr_id` из локального CSV загружаются при запуске. Новые или изменённые пары можно отправить через `POST /api/v1/registrations`.
3. Эмулятор или трекер посылает NDTP-пакеты на TCP `9201`. Для локальной проверки есть `POST /api/v1/telemetry` с декодированным JSON.
4. Если известен факт прохождения предыдущей остановки, источник отправляет `POST /api/v1/arrivals/{arrival_id}/observed`. Бэкенд рассчитывает `current_dev_s = actual_at - planned_at`. При отсутствии факта поле передаётся в ML как `null`, и встроенный в модель `SimpleImputer` заполняет его медианой.

Текущее расписание, наблюдения, последние пакеты и прогнозы хранятся **в памяти одного процесса**. После перезапуска текущее расписание нужно загрузить заново. При выходе целевой остановки из окна `(T+10, T+15]` она сохраняется до планового прибытия: новые свежие пакеты пересчитывают прогноз через ML. После прибытия или при устаревшей телеметрии сохраняется последний результат со статусом `last_known`. Если впереди есть остановка, но до неё больше 15 минут, бэкенд показывает её план и статус `outside_horizon`, не выдавая неподтверждённую экстраполяцию ML. `no_target` остаётся только при полном отсутствии расписания и прежнего прогноза.

## Исторические данные и непрерывный replay

`dataset/<split>/traffic.csv` загружается как телеметрия; `schedule_plan.csv` (validate) или `schedule.csv` (train/test) — как расписание. `points.csv` или `labels_*.csv` даёт момент `T`, целевую остановку и `cur_dev_s`. Целевой `target_delay_s` в бэкенд **не загружается**. Для прогноза используются только пакеты с `event_time ≤ T`. В train/test факт предыдущей остановки учитывается только после её `actual_at`.

- `GET /api/v1/timeline` показывает диапазон времени, шаг `15` секунд и число точек.
- `POST /api/v1/replay/step?sample_id=131672_1767670500` строит контрольный исторический срез и вызывает ML API.
- `POST /api/v1/replay/reset`, затем `POST /api/v1/replay/start?interval_s=1` запускают непрерывное воспроизведение по 15 секунд исторического времени за один шаг. `stop` останавливает, `status` показывает позицию.
- `GET /api/v1/snapshot?mode=historical&at=2026-01-06T03:35:00` получает произвольный срез. `GET /api/v1/stops?mode=historical` возвращает всё историческое расписание для немедленной отрисовки остановок.

Исторический и текущий поток помечены в JSON полем `mode`. Оба публикуют `{ "type": "snapshot", "data": ... }` в `WS /api/v1/ws`. Поле `dataset_split` указывает разбиение для исторического среза. На одну минуту replay приходится четыре шага; `interval_s` задаёт паузу между шагами на часах пользователя.

У каждого автобуса есть `schedule_deviation_s`, `segment_speed_kmh`, `idle_time_s` и `doors_closed`. Скорость сегмента рассчитана по последовательным валидным GPS-точкам за последние 15 минут; простой — сумма наблюдаемых интервалов, где обе соседние скорости ≤1 км/ч. Интервалы больше 120 секунд не экстраполируются. В имеющихся CSV состояния дверей нет; стандартный `autoGenerate` эмулятора не отправляет ячейку IRMA. Поэтому `doors_closed=null`, пока источник не передаст статус через JSON `POST /api/v1/telemetry` или ячейку NDTP `G6CellIrma04`. Для IRMA бэкенд читает битовую маску присутствия и закрытости четырёх дверей; `true` означает, что все присутствующие двери закрыты, `false` — хотя бы одна открыта.

## Контракт с ML

Бэкенд отправляет `POST {ML_SERVICE_URL}/predict` с полями `forecast_time`, `target_time_begin`, координатами целевой остановки, свежестью последнего сообщения, скоростями и их агрегатами за 1/3/5 минут, расстоянием и `current_dev_s`. Формулы окон, GPS-валидности и остановок взяты из `ml_core/prepare_data.py`; телеметрия после `forecast_time` не используется. Входные данные валидируются локальной схемой `MLPredictionRequest`.

Сервис ML возвращает `prediction_delay_s`, `horizon_minutes`, `model_version`, `patterns`. Бэкенд добавляет прогноз к плановому прибытию, относит задержку к `green` (≤60 с), `yellow` (>60 с) или `red` (>120 с) и передаёт паттерны в прогноз и предупреждение. Паттерны показывают наблюдаемые условия движения, а не доказанную причину задержки. Вероятность ML API не выдаёт; `delay_probability` остаётся `null`.

При недоступности ML бэкенд использует последнее известное `current_dev_s` как `baseline`. Если его нет, `forecast_status=insufficient_data`. Тайм-аут запроса к ML — 2 секунды. Повторный инференс одной пары автобус/прибытие ограничен интервалом 15 секунд.

## API для фронтенда и интеграций

| Метод | Назначение |
|---|---|
| `POST /api/v1/registrations` | Привязать `unit_id` к `tr_id` |
| `POST /api/v1/arrivals` | Добавить или обновить плановое прибытие |
| `POST /api/v1/arrivals/{arrival_id}/observed` | Записать фактическое прибытие и текущее отклонение |
| `POST /api/v1/telemetry` | Подать один декодированный пакет для интеграционной проверки |
| `GET /api/v1/snapshot` | Начальный срез автобусов, прогнозов и предупреждений |
| `GET /api/v1/vehicles`, `/vehicles/{tr_id}` | Состояние автобусов |
| `GET /api/v1/alerts`, `/predictions`, `/stops` | Предупреждения, прогнозы и полное расписание остановок (`mode=historical` или `live`) |
| `WS /api/v1/ws` | Последующие сообщения `{ "type": "snapshot", "data": ... }` |
| `GET /api/v1/metrics` | Метрики вызовов ML и приёма пакетов |
| `GET /api/v1/timeline`, `/replay/status` | Диапазон и состояние исторического воспроизведения |
| `POST /api/v1/replay/step`, `/start`, `/stop`, `/reset` | Исторические срезы и непрерывный replay |

`GET /api/v1/snapshot` и `WS /api/v1/ws` — контракты данных для интерфейса; HTML, карта и графика находятся вне бэкенда. WebSocket не отображается в Swagger, поскольку OpenAPI описывает HTTP-запросы.

Исторический `POST /api/v1/replay/step?advance_s=60` продвигает поток на минуту. В `track_points` ответа находятся **все** пакеты за интервал; у пакетов без валидного GPS координаты `null`. `processed_packets` — число прочитанных пакетов с начала датасета. Режим карты не теряет пакеты между кадрами при шаге 15–300 секунд. Во фронтенде запросы идут последовательно, поэтому каждый ответ попадает в отрисовку. `stops` содержит остановки активных машин в окне от 5 минут до кадра до 30 минут после него.

`POST /api/v1/emulator/start` запускает три демонстрационных устройства через REST-API контейнера эмулятора; он передаёт настоящие NDTP-кадры на порт `9201`. Для них бэкенд создаёт демонстрационные плановые остановки, чтобы прогноз ML можно было увидеть сразу. `POST /api/v1/emulator/stop` останавливает отправку; `GET /api/v1/emulator/status` показывает состояние. Последние точки живого потока доступны через `GET /api/v1/tracks?source=ndtp`.

## Проверка через Swagger

1. Откройте <http://127.0.0.1:8000/docs> и вызовите `POST /api/v1/registrations` с `{"tr_id":7,"unit_id":77}`.
2. Вызовите `POST /api/v1/arrivals` с `{"arrival_id":700,"tr_id":7,"planned_at":"<T+12 минут>","lon":37.6176,"lat":55.7558}`. Вместо `<T+12 минут>` подставьте время по Москве примерно через 12 минут от текущего момента.
3. Вызовите `POST /api/v1/telemetry` с `{"unit_id":77,"event_time":"<текущее T>","lon":37.61,"lat":55.75,"speed_kmh":20,"location_valid":true}`. Время используйте в том же формате ISO 8601.
4. В ответе проверьте `vehicles[0].prediction.source="ml"`, `model_version="extratrees-all-42"` и `patterns`. В `GET /api/v1/metrics` счётчик `ml_success` должен увеличиться.

При разовом пакете часть окон скорости остаётся пустой; ML API принимает их как `null`. Для реалистичного примера отправьте несколько пакетов с разными `event_time` в последние пять минут.
