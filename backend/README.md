# Бэкенд диспетчера

Сервис реализует бэкенд-контур задания: принимает NDTP, связывает телеметрию с планом, передаёт исходные данные отдельному ML-сервису и отдаёт состояние карте и карточкам предупреждений. Бэкенд не рассчитывает ML-признаки; сервис в `model/` делает это и применяет `catboost_all.cbm`. Обучение модели и интерфейс дашборда здесь не реализованы.

## Запуск

Из корня проекта установите зависимости:

```powershell
python -m pip install -r backend/requirements.txt
python -m pip install -r model/requirements.txt
```

Без Docker сначала запустите ML-сервис в отдельном окне PowerShell:

```powershell
python -m uvicorn model.app:app --port 8081
```

Затем запустите бэкенд в другом окне PowerShell, задав адрес ML-сервиса **до** старта:

```powershell
$env:ML_SERVICE_URL = "http://127.0.0.1:8081"
python -m uvicorn backend.app.main:app --reload --port 8000
```

Если бэкенд уже работает без `ML_SERVICE_URL`, его нужно перезапустить. Для запуска только бэкенда с резервным прогнозом не задавайте `ML_SERVICE_URL`. ML Swagger: <http://localhost:8081/docs>.

Swagger: <http://localhost:8000/docs>, OpenAPI JSON: <http://localhost:8000/openapi.json>. Если порт 9201 занят, задайте `NDTP_PORT` или `NDTP_ENABLED=0`.

Статическая документация по коду находится в `backend/docs/code`; для обновления выполните `python backend/generate_docs.py`.

По умолчанию загружается только `validate`. Для исторического воспроизведения другого периода задайте `DATASET_SPLIT=test` или `DATASET_SPLIT=train`. Бэкенд читает из разметки лишь `sample_id`, `tr_id`, `T`, целевое плановое прибытие и предоставленный `cur_dev_s`: `target_delay_s` не загружается. Фактическое время из расписания train/test также не используется для расчёта признаков. Одновременно загружается только один период.

Docker (из папки `backend`):

```powershell
docker compose up --build
```

Compose поднимает бэкенд и локальный сервис модели; бэкенд обращается к нему по `http://ml:8081`. `dataset` монтируется в бэкенд в режиме чтения. Для внешнего ML-сервиса переопределите `ML_SERVICE_URL`. `ML_HISTORY_MINUTES` задаёт длину сырой истории для ML (по умолчанию 15 минут, допустимо 1–120). Дашборд остаётся отдельным сервисом команды. Для эмулятора: `targetHost=host.docker.internal`, `targetPort=9201` при локальном запуске контейнера на Windows; для других Docker-сетей используйте адрес сервиса `backend`.

## API для фронтенда

| Запрос | Назначение |
|---|---|
| `GET /api/v1/snapshot?at=2026-01-06T03:35:00` | Полное состояние: автобусы, остановки, предупреждения и счётчики |
| `GET /api/v1/vehicles?mode=historical&min_lon=37.3&risk=red` | ТС в области карты и фильтр риска |
| `GET /api/v1/vehicles/{tr_id}` | Карточка ТС и прогноз |
| `GET /api/v1/stops?at=...&before_min=0&after_min=60` | Плановые остановки как точки карты |
| `GET /api/v1/alerts` | Карточки рисков |
| `GET /api/v1/predictions` | Все доступные прогнозы текущего среза |
| `GET /api/v1/timeline` | Доступные моменты исторического прогона |
| `POST /api/v1/replay/step?sample_id=131672_1767670500` | Опубликовать исторический срез в WebSocket |
| `POST /api/v1/replay/start?interval_ms=1000` | Последовательно воспроизвести все прогнозные моменты |
| `POST /api/v1/replay/stop`, `POST /api/v1/replay/reset`, `GET /api/v1/replay/status` | Пауза, сброс и состояние воспроизведения |
| `WS /api/v1/ws` | Сообщения `{ "type": "snapshot", "data": ... }` при новом пакете или шаге воспроизведения |
| `POST /api/v1/telemetry` | Ввод уже раскодированной телеметрии для локальной интеграции |
| `GET /api/v1/metrics` | Запросы ML, перцентили задержки ML и обработки пакета, дубли и потери WebSocket |

Параметр `mode=live` выбирает текущий поток NDTP. Без него используется исторический период из `DATASET_SPLIT`. Время CSV не содержит часового пояса; рабочее соглашение сервиса — московское местное время. Параметры API с явным смещением (`Z`, `+03:00`) приводятся к нему. `stale=true` означает, что последний пакет старше 90 секунд; `location_stale=true` — последняя достоверная GPS-точка старше 90 секунд. При потере GPS координаты последней достоверной точки сохраняются в `lon`/`lat` вместе с `location_observed_at`. Фронтенд должен обозначить такой маркер устаревшим. `forecast_status` различает `ml`, `baseline`, `no_target`, `insufficient_data`, `unknown_vehicle`; отсутствие прогноза не окрашивается зелёным. Поля `risk` (green/yellow/red/unknown) и `source` (`ml`/`baseline`) сохраняют происхождение оценки. Красный риск ставится при прогнозе опоздания более 120 секунд, жёлтый — более 60 секунд. Это правила визуализации, а не модельная вероятность.

`at` среза, `observed_at` телеметрии, `prediction.at`, `target_arrival.planned_at` и `prediction.predicted_arrival` — разные моменты. `prediction.horizon_s` показывает горизонт именно в момент расчёта. `alert_id` состоит из транспорта и ID планового прибытия и остаётся одинаковым при обновлениях; `updated_at` меняется. `prediction.delay_probability` остаётся `null`, если ML не вернул проверяемую вероятность. Объяснение `reason` от ML следует показывать как предполагаемую причину. Массив сырых пакетов и признаки ML фронтенду не передаются.

В предоставленных CSV **нет ID маршрута и геометрии маршрутной линии**. `tt_action_item_id`/`target_stop_id` — ID **конкретного планового прибытия**, а не постоянный ID физической остановки. Поле `arrival_id` использует точное имя семантики; `stop_id` оставлено как совместимый псевдоним. Поэтому API возвращает плановые прибытия и ТС с `tr_id`; фронтенд может рисовать их точки, но не должен выдавать соединение точек за официальный маршрут. В `traffic.csv` также нет состояния дверей. В NDTP-кадре сейчас разбирается `G6CellNav00`; остальные ячейки безопасно игнорируются. Для отображения статуса дверей нужен отдельный декодер `G6CellIrma04` по согласованному бинарному layout и источник таких пакетов.

## Контракт ML-сервиса

Бэкенд вызывает `POST {ML_SERVICE_URL}/predict` с JSON:

```json
{
  "sample_id": "131672_1767670500",
  "tr_id": 131672,
  "T": "2026-01-06T03:35:00",
  "target_stop_id": 53700172828,
  "target_time_begin": "2026-01-06T03:50:00",
  "target_geom": "POINT (37.85912214 55.73034153)",
  "cur_dev_s": 274.0,
  "telemetry_history": [
    {
      "packet_id": "-5517330596532505101",
      "tr_id": 131672,
      "unit_id": 985940,
      "event_time": "2026-01-06T03:34:45",
      "device_event_id": 0,
      "location_valid": true,
      "gps_time": "2026-01-06T03:34:45",
      "lon": 37.85765,
      "lat": 55.739212,
      "alt": 158.0,
      "speed": 9.0,
      "heading": 240.0,
      "receive_time": "2026-01-06T03:34:47.948198",
      "is_hist_data": false
    }
  ]
}
```

Здесь показан **один** реальный пакет для примера структуры; обычный запрос содержит все доступные пакеты ТС из окна до `T`. Поля внутри `telemetry_history` повторяют столбцы `traffic.csv`. Для NDTP отсутствующие в протоколе поля передаются как `null`, а навигация заполняется из `G6CellNav00`. Backend нормализует поток, выбирает цель и отсекает будущие пакеты. Средние скорости, простои и расстояние рассчитывает сервис `model/`; формулы и границы проверены по `test_features_353.csv` и описаны в `model/README.md`.

Ответ локальной модели для этого примера при наличии всей истории до `T`:

```json
{
  "status": "ok",
  "prediction_s": 170.71267145156406,
  "delay_probability": null,
  "model_version": "catboost_all:f4f4b1190d7e",
  "pattern": null,
  "reason": null
}
```

При успешном ответе обязателен `prediction_s`; `status` по умолчанию `ok`. ML может ответить `{"status":"insufficient_data","prediction_s":null}`. Остальные поля опциональны. Задержка в секундах, знак важен. Локальный `catboost_all.cbm` возвращает только число секунд и версию модели: он не даёт проверенной вероятности, поэтому `delay_probability=null`. При недоступности ML или недостатке данных бэкенд использует предоставленный в прогнозной точке `cur_dev_s` не старше пяти минут и помечает `source=baseline`; без него прогноз отсутствует (`forecast_status=insufficient_data`). В live-потоке `cur_dev_s` неизвестен. Локальный сервис модели также возвращает `insufficient_data` без него, поскольку в предоставленной таблице модель обучалась только с заполненным `current_dev_s`. Тайм-аут вызова ML — 1,5 секунды. Повторный инференс одной live-пары ТС/прибытие ограничен интервалом 15 секунд.

Правило горизонта: первое плановое прибытие строго в `(T+10 минут, T+15 минут]`. Вход ML содержит лишь телеметрию с `event_time <= T`. Для исторического `validate` точки из `points.csv` сопоставляются с `schedule_plan.csv`; факта этого периода сервис не читает. NDTP `unitId` связывается с `tr_id` по телеметрии выбранного периода. Неоднозначные `unitId` не сопоставляются автоматически и отображаются в `/health/ready`. Неизвестный `unitId` показывается как `unit:<id>` без расписания и прогноза.

Эмулятор ставит текущую дату, а расписание относится к январю 2026 года. Для демонстрации можно **явно** задать `DEMO_SCHEDULE_SHIFT_DAYS` — целое число дней сдвига расписания (например, 262 для 25 сентября 2026 года). `mode=live` тогда выбирает сдвинутые плановые прибытия, а ответ содержит `demo_schedule_shift_days`; это демонстрационный режим, **не проверка точности** на случайном движении эмулятора. Необходимо настроить эмулятор на известные `unitId` из выбранного периода. Backend не оценивает прохождение остановки по GPS: если ML-команде нужен такой признак, она рассчитывает его в своей модели из исходных пакетов и расписания.

## Стыковка в общей системе

1. Локальный сервис `model/` или внешний сервис ML-команды поднимает `/predict` по контракту выше; бэкендер задаёт `ML_SERVICE_URL`.
2. Фронтенд использует `/snapshot` как начальную загрузку и `/ws` для обновлений, показывает время среза и `source` в карточке.
3. Для демо исторических прогнозов вызовите `/api/v1/timeline`, затем `/api/v1/replay/step` с выбранным временем или `sample_id`; для автоматического потока вызовите `/api/v1/replay/start`.
4. Для живого NDTP загрузите образ эмулятора из `dataset/ndtp-telemetry-emulator.tar` и отправьте его пакеты на TCP 9201 по инструкции `dataset/docs/Emulator-and-Telematic-Packets-Specification.md`.

Ограничение текущего прототипа: состояние и WebSocket-подписчики хранятся в памяти одного процесса. Запускайте один worker; для горизонтального масштабирования понадобится общая очередь/хранилище. Исторические CSV загружаются при старте; при изменении файлов перезапустите сервис.
