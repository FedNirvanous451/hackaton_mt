# Сверка backend с тремя roadmap

Актуально для этого репозитория. Подробный запуск и API: `backend/README.md`.

| Пункт backend-roadmap | Состояние |
|---|---|
| Отдельный FastAPI, HTTP-контракт ML, OpenAPI, API состояния/прогнозов/остановок | Сделано в `backend/app`; локальный сервис модели в `model/` работает отдельно от backend; frontend остаётся самостоятельным сервисом команды |
| Единые единицы и времена | Задержка/возраст — секунды, скорость — км/ч, координаты — градусы; рабочее соглашение для времени CSV — Москва; поля `at`, `observed_at`, `received_at`, план/прогноз разведены |
| ID целевого прибытия | `arrival_id` — ID планового события; старое `stop_id` сохранено как совместимый псевдоним, физическую остановку оно не идентифицирует |
| Владение ML-признаками | Backend передаёт только исходные поля `traffic.csv`, `cur_dev_s`, `T` и целевое плановое прибытие; признаки рассчитывает отдельный сервис `model/` по таблице ML-команды |
| Исторический поток и часы | Телеметрия сортируется по времени события; есть `/replay/start`, `/stop`, `/reset`, `/status`, `/step`; скорость задаётся `interval_ms`; ML получает ограниченное сырое окно (по умолчанию 15 минут) |
| Горизонт и отсутствие утечки | Первое прибытие в `(T+10, T+15]`; телеметрия только `<=T`. В `validate` нет факта. В `train/test` backend не использует фактическое время прибытия и не читает `target_delay_s` из labels |
| NDTP | TCP-фрейминг, CRC, handshake, `G6CellNav00`, преобразование координат/времени, реконнект и несколько пакетов в одном соединении реализованы и покрыты локальными тестами |
| Сопоставление транспорта | `unit_id → tr_id` проверяется на неоднозначность; неизвестные ID не получают выдуманное расписание |
| Признаки и качество | 14 входов модели воспроизведены на всех 353 строках тестовой таблицы без расхождений; `time_sin/time_cos` восстановлены из названий признаков и границ модели, поскольку в таблице их нет. Производные признаки не попадают в ответ фронту |
| Текущая задержка в live | Backend не оценивает прохождение остановки по GPS; live-поток без ML и без предоставленного `cur_dev_s` имеет явный статус `insufficient_data` |
| Повторы и инференс | Старые и повторные пакеты отбрасываются; повторный live-инференс одной пары ТС/прибытие ограничен 15 секундами; предупреждение имеет стабильный ID |
| Отказы и метрики | Резервный прогноз `cur_dev_s`, отсутствие прогноза как статус, последняя GPS-позиция, stale-флаги, ограниченные WebSocket-очереди; `/metrics` содержит p50/p95 ML и обработки пакета |
| Docker и документация | Compose поднимает backend и локальный сервис CatBoost; есть Dockerfile, Swagger и README обоих сервисов. Frontend подключается отдельно |

## Что зависит от команды и проверки на машине

- **ML:** локальный `/predict` подключён к `catboost_all.cbm`, версия определяется по хешу файла. Вероятность риска модель не выдаёт. Для live-потока `cur_dev_s` отсутствует; сервис честно возвращает `insufficient_data`, пока ML-команда не даст проверенный способ работы без этого признака.
- **Дашборд:** подключение к `/snapshot` и `/ws`, отображение `forecast_status`, свежести GPS, `arrival_id`, `demo_schedule_shift_days`; бэкенд отдаёт необходимые поля. Геометрии маршрутов и постоянного ID остановки в данных нет.
- **Общая сборка:** Compose содержит backend и локальный ML-сервис; frontend сервис добавит его владелец при интеграции.
- **Реальный эмулятор и нагрузка:** официальный эмулятор уже присылал NDTP-пакеты для `unit_id=985940`; в live-срезе менялись время и координаты. Измерение нагрузки с указанием оборудования ещё нужно. `DEMO_SCHEDULE_SHIFT_DAYS` явно переносит январское расписание на дату демонстрации и не служит оценкой точности модели.
